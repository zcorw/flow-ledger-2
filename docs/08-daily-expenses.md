# 每日开销与网页 OCR

访问 `/expenses` 或左侧“每日开销”。本轮是用户追加的消费记录功能，独立于既有资产快照和债权债务。项目品牌和原有资产统计口径保持不变。

## 使用与边界

- 手工录入、编辑和删除开销；金额、币种、消费日期必填，分类默认“未分类”，可逐笔修改。商户、支付账户和备注可选。
- 日期范围、币种及分类可组合筛选；列表每页 50 笔，汇总覆盖整个筛选范围。按币种、按日与币种、按分类与币种分别汇总，不跨币种相加。
- 仅记实际消费。转账和信用卡还款不应再记为消费；本轮没有退款冲销、预算、报销、账户余额扣减或实时总账。
- “返回”保留当前页面内的草稿；关闭浏览器或离开该功能不持久化草稿和原图。

## 保存和数据结构

新增 `expenses` 表，迁移 `0010_daily_expenses`。金额在 PostgreSQL 使用 `numeric(20,6)`，开发 SQLite 使用固定小数文本，避免 SQLite NUMERIC 的浮点精度损失。API 和汇总使用 Decimal，前端以字符串传递、格式化金额。

消费日期是 `YYYY-MM-DD` 的日历日期，不接受时间戳或隐式时区换日。所有接口复用现有 session 认证，并按 `user_id` 限定记录、关联账户和汇总；增改删写入审计。

新增接口：

| 接口 | 用途 |
| --- | --- |
| `GET /api/v1/expenses` | `startDate/endDate/currency/category/offset/limit` 筛选、列表与汇总 |
| `GET /api/v1/expenses/accounts` | 当前用户可关联账户 |
| `POST /api/v1/expenses` | 新增；需 UUID `requestKey`，来源为 `manual` 或 `receipt_ocr` |
| `PUT /api/v1/expenses/{id}` | 修改可编辑字段 |
| `DELETE /api/v1/expenses/{id}` | 从开销记录和汇总中移除 |

每个录入草稿复用同一请求键；数据库唯一约束 `(user_id, request_key)` 保证并发重试只生成一笔。相同键和不同内容返回 409，避免静默覆盖。删除保留幂等墓碑，延迟重试不会重建记录。疑似重复按同日、币种、金额、商户提示 409；用户明确选择“确认仍保存”后可录入合法相同消费，不自动合并。

备份格式升级到版本 2，显式加入开销表和恢复顺序；保留金额、来源、分类、请求键和删除状态。可恢复没有开销表的版本 1 备份；作为全量恢复，这会清空当前开销，恢复为旧备份的状态。恢复仍沿用原有重认证、预备份和事务。

迁移检查还发现旧迁移 `0003` 已存在的汇率索引 `idx_fx_rates_currency_date` 未登记在 ORM；只补了模型元数据以匹配旧迁移，没有删除索引或修改历史迁移。

## 浏览器本地识别

Tesseract.js 与 core 固定为 7.0.0，官方日文和英文模型包固定为 1.0.0，完整性由 pnpm lockfile 固定。`frontend/scripts/prepare-ocr.mjs` 在 dev/build 前复制 worker、各 WASM core 和 `jpn/eng` 语言模型到同站 `/ocr`。不执行 CDN 脚本，不调用云 OCR。构建后的页面首次识别仍需下载同站引擎和模型，不能称作零下载。

模型压缩文件约 5 MB，构建产物包含约 45 MB 的各平台 core；浏览器只加载适用的 core。路径来自应用 BASE_URL，worker 中显式设置资源路径。OCR 依赖按需进入独立 worker，不进入初始页面包。协调 worker 负责整个生命周期，取消、90 秒超时、关窗或离开页面时终止，并通过任务代次忽略旧结果。

图片只在浏览器内存处理。只支持 PNG/JPEG，限制 8 MB、2000 万像素、单边 10000 像素；先校验文件头和尺寸。识别进度、失败、取消均有提示，失败保留原草稿并允许手工录入。确认后 API 只收到结构化字段，不收到原图或 OCR 原文。

`receiptParser.ts` 是独立的文字到字段适配层。只取明确合计/实付标签后的一个金额，排除小计、税额行、商品行、预付款和找零；支持“合計（税込）”及总额后附税额。多个金额/日期、¥ 币种歧义、非法日期会留空并提示。分类不自动推断。候选须人工核对并勾选确认后保存。

## 实际 OCR 效果

在 Chromium 真实运行固定引擎和日英模型，使用 Canvas 生成的合成日文票据，无真实交易信息：

- 清晰样例 `合計（税込） 1234円`：实际读出金额 1234、日期 2026-11-01，分类保持未分类；用户修改分类后确认入账。
- 含千位分隔符样例 `合計（税込） 1,234円`：实际引擎返回 `1.234円`。解析器不猜测为 1234，将日元小数候选留空并提示；测试人工改为 1234、再次核对并确认后保存。
- 部分商品名和税额文字有误识别，保留完整真实输出作为证据。因此每张票据仅形成一笔合计候选，不按商品明细自动拆账。置信度是引擎文字指标，不等于字段准确率。

当前重点是清晰横排日文及英文印刷票据；弯折、反光、模糊、竖排、手写和复杂支付版式未保证准确。PDF/HEIC、眼镜 SDK、语音和硬件输入未接入。

## 验证方式

质量命令及最终结果保存在 `docs/09-expense-validation.md`。截图、实际 OCR 原文及请求 URL 证据由 `e2e/expenses.spec.ts` 输出到 `test-results/expense-evidence`，该目录只有合成数据。前端 `ocr.test.ts` 的模拟 Worker 只用于取消、超时和晚到消息等故障测试；实际识别由浏览器 E2E 执行，不使用 mock 识别结果。

后端测试使用内存或新建临时合成数据库，迁移测试覆盖从基线升级、schema check、降级到 0009、再升级和再 check。E2E 使用新建临时库与 4186/8016 专属端口，禁止复用已有服务；不删除项目中现存数据库，测试后端显式禁用开发 .env 加载。尚未在真实 PostgreSQL 服务或真实手机硬件上运行本轮测试。
